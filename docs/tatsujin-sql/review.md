# 達人に学ぶSQL徹底指南書 第2版 振り返りメモ

各章の「何が主役か」を一言で押さえ直すための要約。

---

## 第1部 魔法のSQL

### 1章 CASE式のススメ

条件分岐の王様は IF文ではなく **CASE式**。文ではなく **「値を返す式」** なので、SELECT / WHERE / GROUP BY / ORDER BY / UPDATE SET など式が書ける場所ならどこにでも書ける。これが `DECODE` や `IF` 関数と比べた最大の強み。単純CASE式より、範囲・複合条件も書ける**検索CASE式**を基本に使う。

**落とし穴**

- 上から評価され最初にマッチした WHEN で打ち切られる。順序ミスで下の条件が死ぬ。
- 全 WHEN/ELSE の戻り値の型を統一する（混在は暗黙変換で事故る）。
- `ELSE` 省略は暗黙の `ELSE NULL`。`SUM(CASE ...)` で事故りやすいので原則明示。
- NULL 比較は `=` ではなく `IS NULL`（`col = NULL` は UNKNOWN）。

---

### 2章 必ずわかるウィンドウ関数

集約関数は「複数行 → 1行」に潰すが、ウィンドウ関数は **行を潰さず、その行の周辺集合への集約結果を列として並べる**。相関サブクエリ（外側の1行ごとに再実行される重いサブクエリ）でしか書けなかった行間比較が一発で書け、可読性・性能ともに改善する。第2版の看板トピック。

**ウィンドウの3要素**

```sql
集約/ランキング関数 OVER (
  PARTITION BY col   -- ① 集合をカット
  ORDER BY col       -- ② カット内で順序づけ
  ROWS BETWEEN ...   -- ③ フレーム（部分集合）
)
```

- 関数分類: 集約系 / ランキング系（`RANK`, `ROW_NUMBER` … ORDER BY 必須）/ 行間参照系（`LAG`, `LEAD` … 7章）。
- `ROWS`=物理的な行数で範囲を切る / `RANGE`=値で切り同値行をまとめる。
- なぜ `ON` でなく `OVER` か: 結合ではなく「窓を覗く」イメージだから。

---

### 3章 自己結合の使い方

同じテーブルに別名を付けて結合するだけで、ループ処理を集合演算に置き換えられる。**非等値結合（`<`, `<>`）** と組むと真価を発揮する。`=` だと自分としか結ばれないが、`p1.name < p2.name` とすれば **{A,B} は出て {B,A} は出ない**＝順番無視の組合せが一発で作れる。

- 「対」の数学: 順序対（順列、`<>`）/ 非順序対（組合せ、`<`）。
- 注意: テーブルを2回スキャンしコストが高い。大きなテーブルでは計測必須で、多くの場面でウィンドウ関数の方が速い。

---

### 4章 3値論理とNULL

SQL は **TRUE / FALSE / UNKNOWN** の3値論理。NULL は「値が無い」マーカーで値ではないので、NULL を含む比較はほぼ全て UNKNOWN になり、**エラーにならず結果だけ間違うクエリ**を生む。

**よくある罠**

- `NOT IN` に NULL が混ざると結果が全部消える / `<>` 除外が NULL を漏らす。
- 集約関数は NULL を無視するが `COUNT(*)` だけは違う。
- `CASE col WHEN NULL` は永遠に真にならない（内部で `=` 比較）。

**推奨**: `NOT NULL` を基本に据える。デフォルト値（区分コード, `9999-12-31`）で代用を検討。「未知（値はあるが不明）」と「適用不能（そもそも存在しない）」を区別したいなら別テーブルや明示フラグで設計する。

---

### 5章 EXISTS述語の使い方

`EXISTS` の背後には **述語論理の量化子（∃ と ∀）** が隠れている。SQL には ∀ の構文がないので、`NOT EXISTS` + `NOT ...` の **二重否定** で表現する。「すべての ◯◯ が P を満たす」を「P を満たさない ◯◯ は存在しない」と言い換えるのが鍵。

- 2値論理で振る舞う（UNKNOWN を返さない）ので、`NOT IN` の NULL 消失の罠を回避できる。
- SELECT リストは `*` / `1` / `NULL` どれも同じ（行の存在だけ見る）。慣習で `SELECT *`。
- 述語を引数に取る点が、関数型言語の**高階関数**に近い。
- 性能: `IN` より早期終了で速いことが多いが、最近のオプティマイザは内部で書き換えるので差が出ないことも。

---

### 6章 HAVING句の力

`HAVING` は GROUP BY の付属品ではなく **「集合の性質」を問う中核機能**。**「WHERE は要素の性質、HAVING は集合の性質」** と二分して捉えるのが本書の流儀。

| 観点 | WHERE | HAVING |
| --- | --- | --- |
| 対象 | 個別の行（要素） | グループ（集合） |
| 使える式 | 列・スカラー値 | 集約関数・グループ列 |

「実体1つに複数行が対応 → 集合だから HAVING」が見極めの方針。集約して1行にしてよいなら HAVING、各行を残したいならウィンドウ関数 + 後置フィルタ。学習のコツはベン図を描くこと。

---

### 7章 ウィンドウ関数で行間比較を行なう

2章のウィンドウ関数を、特に **前後の行・N行前後との比較** に使う応用編。自己結合や相関サブクエリで書いていた処理を `LAG`/`LEAD` で劇的に簡素化できる。

- `LAG(col, n)` / `LEAD(col, n)`: n行前 / n行後の値。
- `FIRST_VALUE` / `LAST_VALUE` / `NTH_VALUE`: 先頭 / 末尾 / n番目。
- 注意: 「N行ずれ」なので `ORDER BY` 必須。日付に欠落があると「1行前」と「1日前」は別物。

---

### 8章 外部結合の使い方

外部結合は「結合」より **「行のレイアウトを変える整形ツール」** と捉える方が本質に近い。

- よくある誤り: `LEFT JOIN` した側の列に `WHERE` 条件を付けると実質 INNER JOIN になる。**「LEFT JOIN 側の条件は ON、ベース側の条件は WHERE」** が原則。
- クロス結合（直積）は「全組合せの土台」を作る道具。「全日付 × 全カテゴリ」を作って実績を `LEFT JOIN` でかぶせれば、**0件のセルも表に出せる**（歯抜けを埋めた集計）。

---

### 9章 SQLで集合演算

SQL は本来「集合の言語」。`UNION` / `INTERSECT` / `EXCEPT`(`MINUS`) を使えば、**1行ずつのループ処理に逃げず、集合レベルで宣言的に書ける**。

- 優先順位: `INTERSECT` が `UNION`/`EXCEPT` より優先。誤読防止に括弧で明示。
- 重複が出ないと分かっているなら `UNION ALL`（ソートを省き高速化）。
- 結果は順序が保証されないので、並べたければ最後に `ORDER BY` を1回だけ。

---

### 10章 SQLで数列を扱う

連番・欠番・連続区間（ギャップ＆アイランド）を、ループや変数なしに集合で解く。本書の宣言型らしさが最もよく出るテーマ。

- 典型: `1,2,3,5,6,8,9,10` から `1–3 / 5–6 / 8–10` の塊を出す。「次が無い＝塊の終わり」「前が無い＝塊の始まり」を `NOT EXISTS` や `LAG`/`LEAD` で表現する。
- 学び: 「ループっぽい問題」を「集合の言い換え」で解くクセが身につく。

---

### 11章 SQLを速くするぞ

「正しい結果」が1段階目、「速いSQL」が2段階目。要するに **原則は2つだけ**。

**原則1: インデックスを殺さない** — 検索条件のカラムに関数・演算・型変換をかけない。

- `SUBSTR(col,...)='abc'` ではなく `col LIKE 'abc%'`（前方一致は効く）。
- 否定形（`<>`, `NOT IN`, `IS NOT NULL`）は基本効かない。
- 暗黙の型変換に注意。文字列カラムに数値リテラル（`= 1500001`）を書くとカラム側が変換され無効化。`= '1500001'` と型を合わせる。

**原則2: 重い処理を早い段階で減らす** — 行数が多いうちにDISTINCT・ソート・結合をやらない。

- `IN`→`EXISTS`、`UNION`→`UNION ALL`、`WHERE`で絞ってから`GROUP BY`、頻繁な集計はView。

**計測**: `EXPLAIN` 等で実行計画を確認。書き換えは推測でなく計画ベースで。

---

### 12章 SQLプログラミング作法

「動けばいい」ではなく **チームで運用できるSQL** を書くための作法。

- **命名・整形**: 意味が汲み取れる名前を、略語は増やしすぎない。インデント・改行を揃え、長い行は JOIN ごと・`OR` ごとに改行。
- **移植性**: 標準SQL を基本に、方言は View / Stored Procedure に隠蔽して局所化。
- **安全策**: `DELETE`/`UPDATE` の WHERE 漏れを避ける（件数確認・トランザクション）。大量更新は分割。DDL は `IF NOT EXISTS` で冪等に。
- **コメント**: **Why を書き、What は書かない**。コードから復元できない背景（ワークアラウンドの理由など）だけ残す。

## 第2部 リレーショナルデータベースの世界（理論編）

### 13章 RDB近現代史

なぜ RDB が主流になり、今どんな壁に直面しているかを歴史軸で押さえる章。階層型 → ネットワーク型 → **リレーショナル（コッド, 1970）** と進み、RDB が勝ったのは「直感的な表モデル + 宣言型の SQL」だったから。

- 現代の課題: ACID を強く守るほどスケールアウトしにくい / 表形式はグラフ・半構造化データ（JSON, ドキュメント）に不向き。
- NoSQL はモデルを単純化し ACID を緩めて（BASE）スケールを得たが、RDB を完全には置き換えていない。

---

### 14章 なぜ"関係"モデルという名前なの?

「表」と「関係（リレーション）」は同じものではない。RDB が「リレーショナル」なのは、背後に **集合論の関係（直積の部分集合）** があるから。レコード間の関連という意味ではない。

- 関係の性質: 行に順序なし / 列に順序なし / 重複行なし / 値は単一値（第1正規形）。
- SQL の表は **マルチセット（重複OK）** なので純粋な関係モデルとズレがあり、ここがバグの温床になる。

---

### 15章 関係に始まり関係に終わる

**関係代数の閉包性** — 関係に演算（選択・射影・結合・和差）を施した結果も「また関係」。だから結果をさらに入力にする合成ができる。

- `SELECT` の結果も表なので、サブクエリ・ビュー・CTE(`WITH`)でネストできる。
- UNIX パイプ（ファイル→ファイル）や関数型の合成（compose）と同じ発想。

---

### 16章 アドレス、この巨大な怪物

RDB 最大の発明は、データから **アドレス（ポインタ）を追放したこと**。コッドの目的は「ループを書かなくて済むDBを作ること」だった。

- ポインタはループを強制し、物理レイアウトに依存し、最適化を阻害する。
- RDB はレコードの関係を **値（外部キー）** で表し、アクセスは集合演算、物理経路はオプティマイザに委ねる。だから **What（何が欲しいか）だけ書けばよい**。手続き型の感覚で書くと詰まるのは、根本のパラダイムが違うから。

---

### 17章 順序をめぐる冒険

関係モデルでは **行に順序がない**。なのに実務では前年比・移動平均・累積・ランキングと順序を扱いたい。この矛盾の解消が **ウィンドウ関数（SQL:1999〜）** 登場の背景。

- ウィンドウ関数は「順序を一時的に持ち込んだ局所領域」で集約する。
- 設計時は順序を持つ列（時系列・版番号）を明示する。`id` 連番に順序を仮定しない。

---

### 18章 GROUP BYとPARTITION BY

両者の違いは一言、**潰すか・潰さないか**。

| | GROUP BY | PARTITION BY |
| --- | --- | --- |
| 集約 | 1グループ → 1行に圧縮 | 圧縮しない（行数は変わらない） |
| 用途 | 集約結果が欲しい | 行を残したまま集計値を付加 |

「部署別の人数」は GROUP BY、「各従業員の隣に自部署の人数を出す」は `COUNT(*) OVER (PARTITION BY dept)`。

---

### 19章 手続き型から宣言型・集合指向へ頭を切り替える7箇条

本書全体のエッセンスを7つに凝縮した総括章。

1. テーブルの行に順序はない（要るなら明示）
2. ループは GROUP BY とウィンドウ関数で置き換える
3. EXISTS と「量化（∃/∀）」を理解する
4. HAVING句が集合指向の本質
5. IF文は CASE式で置き換える
6. テーブルを行の列挙でなく「集合」とみなす
7. ベン図を描いて和・積・差で考える

---

### 20章 神のいない論理

2値論理（真/偽）は「全知の神の論理」。現実には「分からない」が常にあるので、SQL の **3値論理は不完全情報を扱うための"神のいない論理"**。

- 未入力・未測定・適用不能を「偽」と同一視するのは情報の捏造なので、第3の値 UNKNOWN が要る。
- 代償は直感に反する挙動（4章の `NOT IN` の罠など）。教訓は **設計で NULL を増やさず3値論理を回避するのが現実解**。

---

### 21章 SQLと再帰集合

SQL は **再帰CTE（`WITH RECURSIVE`）** で木構造・グラフ探索を扱える。これは集合論の再帰的定義（フォン・ノイマンの自然数構成: `0:=∅`, `n+1:=n∪{n}`）に裏打ちされている。

- 「初期値 + 漸化式」という構造が `WITH RECURSIVE` そのもの。
- 組織図・部品表(BOM)・カテゴリ階層・フォロー関係に応用。ループしないよう `UNION` で重複排除。

---

### 22章 NULL撲滅委員会

> **「NULL は薬。正しく使えば有用だが、乱用すれば全てをぶち壊す」**

NULL を徹底的に減らす設計が、結局はバグも性能問題も減らすという強い主張（4章の実践版）。

- 害: 3値論理の伝染 / インデックスが利きにくい / 集約関数の例外的挙動 / `NOT IN` で結果消滅。
- 指針: `NOT NULL` を基本に、デフォルト値を設定、「未知」と「適用不能」は別テーブルやフラグで区別。どうしても必要なら `COALESCE` で変換してから使う。

---

### 23章 SQLにおける存在の階層

SQL は「ある / ない」の表現が **多層化** している。混同すると思わぬバグになる。

| レベル | 意味 |
| --- | --- |
| 行が存在しない | `NOT EXISTS` / 外部結合の NULL 行 |
| 集合として空 | `COUNT(*) = 0` |
| 値として NULL | 行はあるが値が不明（`IS NULL`） |
| 空文字列 / ゼロ | 値はあるが内容が空・意味的に無 |

- 「行が無い」と「値が NULL」を混同しない（外部結合の NULL は"マッチ無し"のサインで元データの NULL とは別物）。
- 空集合の `SUM` は NULL を返す（0 ではない）ので `COALESCE` で 0 に変換する。
- 最終章メッセージ: **SQL は集合・述語論理・3値論理が絡み合った「存在を扱うための言語」**。

---

## 全体総括

- SQL は手続き型の浅い理解では中級者になれない。**関係モデル・集合論・述語論理**を背後に意識すると、コードが短く・速く・正しくなる。
- **ウィンドウ関数**は SQL の表現力を一段引き上げた、第2版を貫くテーマ。
- **NULL は減らす**。設計で避けられる3値論理は避ける。
