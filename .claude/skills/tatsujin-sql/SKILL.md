# 達人SQL徹底指南書 1章ずつ学習ワークフロー

このスキルは「達人に学ぶSQL徹底指南書 第2版」を、このリポジトリの実コードに照らし合わせて1章ずつ深掘りするためのワークフローです。**1回の起動で1章だけ**を扱います。

## このスキルが各章で出力する2つの観点

1. **現状分析・改修**: その章のテーマに該当する箇所を既存コード（migration / Go クエリ / TS フロント集計）から洗い出し、良い点と改善余地を整理して、必要なら改修する。
2. **発展提案**: このプロダクト（[`README.md`](../../../README.md) の「学生・教員が記事・質問・回答・制作物を投稿し知識共有/フィードバックする情報共有サイト」というコンセプトと PBI 一覧）を踏まえ、**その章のテクニックが主役になる新機能・新しい集計の仕組み・既存機能の発展系**を提案する。

観点1は「いまのコードをどう良くするか」、観点2は「このアプリをどう伸ばせるか」。**両方とも、その章の SQL テクニックと結びつける**のがこのスキルの肝です。理論章（第2部）など既存コードに該当が無い章でも、観点2でプロダクトの設計・発展を語れるようにしておくこと。

## 入力

- 章番号が引数で渡された場合（例: `3`, `第3章`, `chapter-3`）→ その章を扱う
- 引数なし → `docs/tatsujin-sql/PROGRESS.md` を読み、最初の「未着手」章を扱う

## 前提

- まとめノート: [`docs/tatsujin-sql-shinansho-summary.md`](../../../docs/tatsujin-sql-shinansho-summary.md)
- 進捗管理: [`docs/tatsujin-sql/PROGRESS.md`](../../../docs/tatsujin-sql/PROGRESS.md)
- 章別分析: `docs/tatsujin-sql/chapter-NN-<slug>.md`

## 設計原則（守ること）

1. **1コマンド = 1章**。複数章を一気に進めない（ユーザのレビュー機会を奪わない）
2. **改修は必須ではない**。該当箇所がない章は分析メモだけ残して終了する
3. **改修前に必ずユーザに確認**。`AskUserQuestion` で複数案を提示し、選択してもらう
4. **git は触らない**。`git add` / `git commit` / `git push` は実行しない（ユーザが行う）
5. **`app/src/api/generated/**` は手で編集しない**（リポジトリのコントラクト規約）
6. **生成された SQL/Go コードはそれぞれの make/npm スクリプトを通す**こと（OpenAPI 経由の型変更が絡む場合）
7. **発展提案は「妄想」で終わらせない**。README の PBI（ユーザーストーリー）に紐づけ、必要なテーブル/クエリの骨子（擬似SQLで可）と規模感（小=クエリ追加のみ / 中=API+UI / 大=スキーマ追加）を必ず添える。**提案はメモに残すのが基本**で、実装するかはユーザーが Step 5 で選ぶ
8. **発展提案でも、その章のテクニックを「主役」にする**。CASE 式の章で単なる CRUD を提案しても学びにならない。「この機能はこの章のテクニックがあって初めて綺麗に書ける」という結びつきを言語化する

## ワークフロー（必ずこの順序）

### Step 1. 進捗確認と章の決定

- `docs/tatsujin-sql/PROGRESS.md` が無ければ、後述のテンプレで作成する
- 引数で章が指定されていればそれを使い、なければ最初の未着手 (`- [ ]`) 章を選ぶ
- 章番号が範囲外 (1-23) ならユーザに知らせて終了

### Step 2. 章テーマとプロダクト文脈の把握

- `docs/tatsujin-sql-shinansho-summary.md` から該当章のセクション（例: `## 3章 自己結合の使い方`）を Read する
- 章の「主張」「典型パターン」「落とし穴」を内的に要約し、リポジトリで探すべきキーワードを決める
  - 例: 3章なら "自己結合", "self join", "CROSS JOIN Products", "重複削除"
  - 例: 4章なら "NULL", "NOT IN", "IS NULL", "COALESCE", "<>"
  - 例: 11章なら `WHERE`/`LIKE '%...%'`, インデックス未利用箇所
- **`README.md` の「プロダクト概要」「PBI（ユーザーストーリー）」「現在の主な機能」を Read する**（観点2の発展提案の土台）。このアプリは「学生・教員が記事・質問・回答・制作物を投稿し、知識共有/フィードバックする情報共有サイト」。評価・ランキング・分類別閲覧・プロフィール・制作物公開など**集計の余地が大きい PBI** が並んでいるので、章テーマと相性の良い PBI に当たりを付ける
  - 例: CASE式 → 「記事の評価サマリ」「質問の回答状況バッジ（未回答/回答あり/解決済）」
  - 例: ウィンドウ関数 → 「人気記事ランキング」「カテゴリ内ランキング」「投稿者の月別投稿推移」
  - 例: 自己結合/再帰 → 「コメントのスレッド階層」「おすすめユーザー（共通タグ）」

### Step 3. リポジトリ内の探索（観点1の材料 + 観点2の足場）

以下3つすべてを対象とする（章テーマに合致する箇所だけ報告）:

1. **SQL ファイル**: `api/migrations/*.sql`
   - スキーマ定義 (CHECK制約, NOT NULL, インデックス) と seed クエリ
2. **Go の埋め込み SQL クエリ**: `api/internal/**/repository/*.go`
   - 文字列リテラル中の `SELECT` / `INSERT` / `UPDATE` / `DELETE`
3. **TS フロントエンドの集計ロジック**: `app/src/**/*.{ts,vue}`
   - 「本来 SQL でやるべき集計をフロントでやっていないか」の観点
   - `app/src/api/generated/**` は対象外（自動生成）

探索方法: Bash で `grep -rni` または `Glob` + `Read`。Explore Agent を使ってもよい。

探索しながら、**観点2（発展提案）の足場**も同時に拾う:

- いま存在するテーブル（articles / tags / likes / replies / users / user_profiles など）で、**この章のテクニックを使えば新しく取り出せる集計・関係**は何か
- 既存機能（記事一覧・いいね・返信スレッド・ベストアンサー）の**自然な延長**で、PBI を満たす未実装の機能はどれか
- 新テーブルを足さなくてもクエリ追加だけで実現できる「軽い発展」を優先候補にする（規模感の判断材料）

### Step 4. 分析メモの作成

`docs/tatsujin-sql/chapter-NN-<slug>.md` を新規作成。スラッグは英小文字ケバブで章タイトル要約（例: `chapter-03-self-join.md`, `chapter-04-null-and-three-valued-logic.md`）。

**ファイル構成テンプレ**:

```markdown
# 第N章 <タイトル>

> 学習日: YYYY-MM-DD  |  関連まとめ: [summary.md#N章](../tatsujin-sql-shinansho-summary.md)

## 章の要旨（3-5行）

<本章で身につけたい考え方を簡潔に>

## このリポジトリでの該当箇所

| 種別 | ファイル:行 | 関連する論点 |
|---|---|---|
| migration | `api/migrations/xxx.sql:12` | 例: NOT NULL 制約が緩い |
| Go クエリ | `api/internal/article/repository/get_list_articles.go:34` | 例: NULL を考慮しない `<>` |
| TS 集計 | `app/src/features/articles/...vue:80` | 例: フロントで filter/sum している |

該当なしの場合は「**該当箇所なし**」と明記し、その理由（このリポジトリの設計上、該当テーマが現れない / 既にベストプラクティスに沿っている など）を1-2行で書く。

## 良い点（リポジトリで既に守れていること）

- ...

## 改善余地

### 案A: <案のタイトル>
- 対象ファイル: ...
- 変更内容: ...
- 期待効果: ...
- 学習ポイント: <この案がなぜ本章の論点と結びつくか>

### 案B: ...

## このアプリの発展提案（新機能・集計アイデア）

> README のプロダクト概要・PBI を踏まえ、本章のテクニックが「主役」になる新機能/集計を提案する。
> 既存コードの改修（上の「改善余地」）とは別枠。実装は任意で、メモに残すだけでもよい。
> 該当する PBI が無い理論章でも、「このテクニックを知っていると、このアプリの設計でどう発展を描けるか」を1案は書く。

### 発展提案1: <機能名>
- 対応する PBI / ユーザーストーリー: <README の No.X、または新規ストーリーを1文で>
- 何ができるようになるか: <ユーザー視点の価値>
- 本章テクニックがどう主役になるか: <この章を知らないと書けない／素朴実装だと破綻する理由>
- 必要なスキーマ・クエリの骨子（擬似SQLで可）:
  ```sql

  ```
- 規模感: 小（クエリ追加のみ） / 中（API + UI） / 大（新スキーマ）
- 既存実装との接続点: <どの handler/repository/コンポーネントに乗るか>

### 発展提案2: ...

## 採用した対応

- 採用した改修案（観点1）: A / B / なし
- 着手する発展提案（観点2）: 提案1 / 提案2 / なし（メモのみ）
- なしを選んだ場合の理由: <学習目的としては読了で十分 / リスクや規模が利点を上回る など>

## 学びの言語化（自分用メモ）

- <この章を読み終えて、今後どう書き方が変わるか>
- <このアプリを伸ばすうえで、この章のテクニックがどんな場面で効くか>
```

### Step 5. ユーザに対応方針を確認

`AskUserQuestion` で以下を聞く。**観点1（既存改修）と観点2（発展提案）を同じ選択肢の土俵に並べる**:

- 質問: 「第N章で着手する対応」
- 選択肢の例: 改修案A / 改修案B / 発展提案1 / 発展提案2 / 「メモのみ（実装しない）」 / 「他（自分で記述）」
- 複数を同時に選びたいケースがあるので、必要なら `multiSelect: true` を使う

**必ず「おすすめ」を1つ提示する**（`AskUserQuestion` の推奨オプション仕様に従う）:

- おすすめにする案を**選択肢の先頭**に置き、ラベル末尾に `（おすすめ）` を付ける
- その案の `description` に「学習効果と規模・リスクのバランスでなぜ一番おすすめか」を1文で書く（例: 「本章のテクニックを最小の変更量で体験でき、既存挙動を壊さないため」）
- おすすめの選び方の目安: **学習効果が高く、かつ規模・リスクが小さい案**を優先（小さく動く単位を尊ぶリポジトリ方針とも整合）。大規模な発展提案より、章のテクニックが主役になる小さな改修・縦切りを推す
- 「おすすめは○○ですが、△△ならより踏み込んだ実装になります」のように**比較の軸も添える**と選びやすい

判断の指針:
- **既存改修が無く、発展提案だけがある章**でも Step 5 は実施する（発展提案を実装するか聞く）
- **どちらも該当が薄い理論章**は確認をスキップし、「メモのみ」として Step 6 に進む
- 発展提案の「大（新スキーマ）」を選ばれた場合は、規模が大きいので**最小の縦切り（1クエリ＋1エンドポイント＋最小UI）から**始めることを提案する

### Step 6. 実装（同意した場合のみ）

- ユーザが選んだ案（改修 / 発展提案）だけを実装する
- **発展提案を実装する場合**も、いきなり大きく作らない。1クエリ＋1エンドポイント＋最小UIの**縦切り**でレビュー可能な単位に収める。新テーブルが要るなら新 migration を追加
- スキーマ変更を伴う場合: 既存 migration を編集せず、新しい migration ファイルを追加する（`api/migrations/YYYYMMDDhhmmss_xxx.{up,down}.sql`）
- Go の SQL を変更した場合: 既存テストが通るかは型検査レベルで判断（実行は別途）
- TS のリファクタは Vuetify ルール (`app/AGENTS.md`) に従う
- **`app/src/api/generated/**` は絶対に触らない**

### Step 7. PROGRESS.md の更新

該当章のチェックボックスを `- [x]` にし、分析メモへのリンクと「改修あり/なし」を追記する。

### Step 8. 完了報告

ユーザに以下を1段落で伝える:

- 扱った章とテーマ
- 分析メモのパス
- 改修したファイル一覧（あれば）
- **出した発展提案の見出しと、実装したもの/メモに留めたものの区別**
- 次に扱うべき章の候補（PROGRESS.md の次の未着手）
- **git の操作は行っていないこと**を明示し、次に何をすべきか（例: `git add ... && git commit`）はユーザ判断であることを伝える

## 注意事項（やってはいけないこと）

- **複数章を一度に処理しない**。1コマンド1章
- **git 操作を実行しない**（`git status` などの読み取りは可、`commit` / `push` / `add` は不可）
- **`app/src/api/generated/**` を編集しない**
- **summary.md を勝手に書き換えない**（誤りを見つけたら指摘するだけ）
- **第2部の理論章で「無理に SQL を書く」ことをしない**。既存コードに該当なし → 観点1は設計メモのみで完結させる。ただし観点2（発展提案）は「このテクニックを知っているとこのアプリをどう設計・発展できるか」を最低1案は書く
- **発展提案を勝手に実装しない**。提案はメモに残すまでが基本で、コードを書くのは Step 5 でユーザが選んだときだけ
- **発展提案を README/PBI から切り離さない**。「あったら便利」ではなく、必ずプロダクトのユーザーストーリーに紐づける
