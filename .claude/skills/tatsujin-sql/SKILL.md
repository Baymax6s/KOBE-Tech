# 達人SQL徹底指南書 1章ずつ学習ワークフロー

このスキルは「達人に学ぶSQL徹底指南書 第2版」を、このリポジトリの実コードに照らし合わせて1章ずつ深掘りするためのワークフローです。**1回の起動で1章だけ**を扱います。

## 入力

- 章番号が引数で渡された場合（例: `3`, `第3章`, `chapter-3`）→ その章を扱う
- 引数なし → `docs/tatsujin-sql/PROGRESS.md` を読み、最初の「未着手」章を扱う

## 前提

- まとめノート: [`docs/tatsujin-sql-shinansho-summary.md`](../../../docs/tatsujin-sql-shinansho-summary.md)
- 進捗管理: [`docs/tatsujin-sql/PROGRESS.md`](../../../docs/tatsujin-sql/PROGRESS.md)
- 章別分析: `docs/tatsujin-sql/chapter-NN-<slug>.md`

## 設計原則（守ること）

1. **1コマンド = 1章**。複数章を一気に進めない（ユーザのレビュー機会を奪わない）
2. **改修は必須ではない**。該当箇所がない章は分析メモだけ残して終了する
3. **改修前に必ずユーザに確認**。`AskUserQuestion` で複数案を提示し、選択してもらう
4. **git は触らない**。`git add` / `git commit` / `git push` は実行しない（ユーザが行う）
5. **`app/src/api/generated/**` は手で編集しない**（リポジトリのコントラクト規約）
6. **生成された SQL/Go コードはそれぞれの make/npm スクリプトを通す**こと（OpenAPI 経由の型変更が絡む場合）

## ワークフロー（必ずこの順序）

### Step 1. 進捗確認と章の決定

- `docs/tatsujin-sql/PROGRESS.md` が無ければ、後述のテンプレで作成する
- 引数で章が指定されていればそれを使い、なければ最初の未着手 (`- [ ]`) 章を選ぶ
- 章番号が範囲外 (1-23) ならユーザに知らせて終了

### Step 2. 章テーマの抽出

- `docs/tatsujin-sql-shinansho-summary.md` から該当章のセクション（例: `## 3章 自己結合の使い方`）を Read する
- 章の「主張」「典型パターン」「落とし穴」を内的に要約し、リポジトリで探すべきキーワードを決める
  - 例: 3章なら "自己結合", "self join", "CROSS JOIN Products", "重複削除"
  - 例: 4章なら "NULL", "NOT IN", "IS NULL", "COALESCE", "<>"
  - 例: 11章なら `WHERE`/`LIKE '%...%'`, インデックス未利用箇所

### Step 3. リポジトリ内の該当箇所探索

以下3つすべてを対象とする（章テーマに合致する箇所だけ報告）:

1. **SQL ファイル**: `api/migrations/*.sql`
   - スキーマ定義 (CHECK制約, NOT NULL, インデックス) と seed クエリ
2. **Go の埋め込み SQL クエリ**: `api/internal/**/repository/*.go`
   - 文字列リテラル中の `SELECT` / `INSERT` / `UPDATE` / `DELETE`
3. **TS フロントエンドの集計ロジック**: `app/src/**/*.{ts,vue}`
   - 「本来 SQL でやるべき集計をフロントでやっていないか」の観点
   - `app/src/api/generated/**` は対象外（自動生成）

探索方法: Bash で `grep -rni` または `Glob` + `Read`。Explore Agent を使ってもよい。

### Step 4. 分析メモの作成

`docs/tatsujin-sql/chapter-NN-<slug>.md` を新規作成。スラッグは英小文字ケバブで章タイトル要約（例: `chapter-03-self-join.md`, `chapter-04-null-and-three-valued-logic.md`）。

**ファイル構成テンプレ**:

```markdown
# 第N章 <タイトル>

> 学習日: YYYY-MM-DD  |  関連まとめ: [summary.md#N章](../tatsujin-sql-shinansho-summary.md)

## 章の要旨（3-5行）

<本章で身につけたい考え方を簡潔に>

## このリポジトリでの該当箇所

| 種別 | ファイル:行 | 関連する論点 |
|---|---|---|
| migration | `api/migrations/xxx.sql:12` | 例: NOT NULL 制約が緩い |
| Go クエリ | `api/internal/article/repository/get_list_articles.go:34` | 例: NULL を考慮しない `<>` |
| TS 集計 | `app/src/features/articles/...vue:80` | 例: フロントで filter/sum している |

該当なしの場合は「**該当箇所なし**」と明記し、その理由（このリポジトリの設計上、該当テーマが現れない / 既にベストプラクティスに沿っている など）を1-2行で書く。

## 良い点（リポジトリで既に守れていること）

- ...

## 改善余地

### 案A: <案のタイトル>
- 対象ファイル: ...
- 変更内容: ...
- 期待効果: ...
- 学習ポイント: <この案がなぜ本章の論点と結びつくか>

### 案B: ...

## 採用した改修

- 採用した案: A / B / なし
- なしを選んだ場合の理由: <学習目的としては読了で十分 / リスクが利点を上回る など>
- 実際に変更したファイル: <あれば列挙>

## 学びの言語化（自分用メモ）

- <この章を読み終えて、今後どう書き方が変わるか>
```

### Step 5. ユーザに改修方針を確認

`AskUserQuestion` で以下を聞く:

- 質問: 「第N章の改修方針」
- 選択肢: 各案 A/B/... と「改修なし（メモのみ）」「他（自分で記述）」

**該当箇所が無い章**は確認をスキップし、「改修なし」として Step 6 に進む。

### Step 6. 改修の実装（同意した場合のみ）

- ユーザが選んだ案だけを実装する
- スキーマ変更を伴う場合: 既存 migration を編集せず、新しい migration ファイルを追加する（`api/migrations/YYYYMMDDhhmmss_xxx.{up,down}.sql`）
- Go の SQL を変更した場合: 既存テストが通るかは型検査レベルで判断（実行は別途）
- TS のリファクタは Vuetify ルール (`app/AGENTS.md`) に従う
- **`app/src/api/generated/**` は絶対に触らない**

### Step 7. PROGRESS.md の更新

該当章のチェックボックスを `- [x]` にし、分析メモへのリンクと「改修あり/なし」を追記する。

### Step 8. 完了報告

ユーザに以下を1段落で伝える:

- 扱った章とテーマ
- 分析メモのパス
- 改修したファイル一覧（あれば）
- 次に扱うべき章の候補（PROGRESS.md の次の未着手）
- **git の操作は行っていないこと**を明示し、次に何をすべきか（例: `git add ... && git commit`）はユーザ判断であることを伝える
